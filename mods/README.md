# ORE Claude Code mods

The six original independent, optional plugins are documented below. Their runtime code is TypeScript and imports only
files inside its own plugin. `ore-progress/hooks/state.ts` is the canonical pure
reader; copies must remain byte-identical (checked by package validation).
There is no runtime dependency between the plugins.

ORE **4.1.0-alpha.1** additionally includes 21 self-contained command adapters.
Their executable behavior, partial capabilities, bundled Python processes and
permissions are described in [runtime adapters](../docs/runtime-mods.md).
The no-process/no-network guarantees below apply to the original six.

## API provenance

`api-types/` is an unedited snapshot generated by Claude Code 2.1.295 on
2026-10-08 when an empty local probe was loaded interactively with `--plugin-dir`.
The installed 2.1.267 and isolated 2.1.295 both rejected `/plugin-types`.
Loading a mod interactively generated `.claude-plugin/types/` instead; the
snapshot preserves those exact declarations for reproducible type checking.
Do not hand-edit them or substitute event names from documentation.

CLI mods require Claude Code 2.1.287+. This implementation was tested on
2.1.295; API compatibility with 2.1.287 itself has not been tested. Regenerate
and type-check against your runtime after upgrades. Generated per-plugin types
are ignored; the reviewable snapshot is kept here. No generated MCP tools were
connected during the probe.

## Events and calls

| Plugin | Events | Host calls beyond the shared reader/status command |
| --- | --- | --- |
| ore-progress | session.start, session.end, ui.render (AbovePrompt), command.run | clock.every, ui.invalidate, ui.resolve |
| ore-guard | session.start, tool.call, command.run | ui.ask |
| ore-resume | session.start, command.run | ui.log |
| ore-gates | session.start, session.end, ui.render (AbovePrompt), turn.complete, tool.call (Bash), command.run | clock.every, ui.invalidate, ui.resolve, ui.log |
| ore-stale-window | session.start, session.end, ui.render (AbovePrompt), command.run | clock.every, ui.invalidate, ui.resolve, ui.log |
| ore-departments | session.start, session.end, ui.render (AbovePrompt), command.run | clock.every, ui.invalidate, ui.resolve |

The shared reader uses `session.cwd` and `fs.read`. Status commands use
`command.register` and return a textual handoff. No mod calls `fs.write`,
network, process, model, environment, settings, or persistent store APIs.
These are audited API calls, not operating-system permission restrictions.
**Mods run with the user's permissions and have no sandbox.**

## State contract and limits

Read `.ore/active.json` as a schema-v1 pointer, validate the task id, then read
`.ore/tasks/<id>.json` and recheck the pointer. Missing, corrupt, malformed or
unsupported state produces no automatic display, warning or interception.
An explicitly requested `/<plugin-name>-status` returns `No valid ORE state`.
`ore_state.py` remains the only `.ore/` writer. Progress is recomputed from
weights with Python's ties-to-even rounding. A completed record stays visible
in progress; resume and guard ignore completed tasks.

Displays compose the existing AbovePrompt tree rather than replacing other
mods. Terminal and Desktop show the band; headless and other surfaces have the
explicit status command. Very small windows may scroll the band; a mod cannot
guarantee all six displays remain simultaneously visible in every layout.
Polling reads every second, skips overlapping reads, cancels on session exit,
and continues across `/clear` and `/resume` (these do not fire session.start).
Reloads trigger a new initial read. State-change alerts report observed
revisions; they cannot identify the writing window or detect a task switch
that occurs and reverses entirely between reads.

Gates list required gates whose status is not passed/not_applicable, together
with blockers. Every ended turn with these outstanding emits a warning;
the mod never interprets the assistant's answer as a completion claim. A Bash
call explicitly invoking `ore_state.py complete` also emits a warning. The
writer itself enforces completion, including deliverables and form integrity.

## Guard

Default patterns cover recursive/forced deletions, DROP/TRUNCATE and common
destructive migration commands, force pushes, explicit production deployments,
credential rotations and package publications. Matching uses tool name and
arguments, never conversation text. The dialog shows the persisted task and
a bounded argument preview, with common inline secrets masked. It labels
impact as unmeasured: no shell, Git, database or remote dry run is executed.
Targets hidden in scripts, aliases, obfuscation or custom tools require custom
patterns. Pattern matching is not a complete shell parser or security boundary.

Only `Proceed once` grants approval for that call. Cancellation, unavailable
headless UI, interruption, errors, and state changes during approval deny it.
Approval then passes to the normal host permission chain; it does not return
an allow verdict. Approval is not persisted. There is no recorded ORE scope
exception/approval ledger, so matching operations ask each time an active or
blocked ORE task exists. No ORE state means the guard is inert.

Configure `patterns` in `/config` or `claude plugin configure ore-guard` as a
JSON array of regex source strings, for example `["release-live", "DROP\\s+TABLE"]`.
A nonempty configured value **replaces** defaults; include all desired rules.
An empty array disables matching. Invalid configuration requires confirmation
for every reviewed tool call. Patterns are trusted configuration: bounded
length/count does not eliminate pathological regex execution times.

## Optional specialist recording

Old records show only `ORE lead`, with no inferred department or history.
To record an identity, use the existing revision-protected update command:

```sh
python skills/ore/scripts/ore_state.py update --repo . --task-id TASK_ID \
  --expect-revision REVISION --active-specialist ore-security-privacy \
  --department "Security & Governance" --domain-lead "Security lead"
```

All three identity arguments are required together. The writer adds optional
`active_specialist: {specialist, department, domain_lead, revision}` and a
structured `specialist_changed` event only when identity changes. Existing
commands are unchanged unless these options are supplied. The mod shows
`ORE lead → domain_lead → specialist` and the last five recorded transitions.
Skills do not automatically record these new fields; hosts opt into this CLI
extension. Display describes persisted assignment, not measured execution.

## Development checks

```sh
python scripts/validate_package.py
python -m unittest discover -s evals -p "test_*.py" -v
claude plugin validate mods/ore-progress
claude plugin test mods/ore-progress
tsc -p mods/ore-progress
claude --plugin-dir mods/ore-progress
```

Repeat the last four commands for all six directories. Node.js 24+ is required
for the Python suite's TypeScript harness; Python checks execute real modules
with a fake read-only host and never execute the intercepted actions. Native
Claude tests also exercise guard approval/cancellation through AskUserQuestion.
